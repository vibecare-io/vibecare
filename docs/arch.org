* Overview

VibeCare is a wellness and routine management system consisting of:
- *Backend*: Go server with gRPC API, SQLite database, RRule-based scheduling
- *Frontend*: Native Swift macOS client (server-centric architecture)
- *Protocol*: Type-safe Protocol Buffers for all communication
- *Build Tool*: Just command runner for development tasks

** Core Components

*** gRPC Server
- *Location*: =backend/cmd/server/main.go=
- *Port*: 50051 (default)
- *Initialization*:
  1. Setup OpenTelemetry
  2. Connect to SQLite
  3. Run migrations
  4. Initialize EventHub
  5. Start scheduler
  6. Register gRPC services
  7. Start HTTP web server

*** Scheduler
- *Location*: =backend/internal/scheduler/scheduler.go=
- *Polling Interval*: 1 minute
- *Responsibilities*:
  - Query database for due schedules
  - Evaluate RRule expressions (using RFC 5545 library)
  - Trigger routine executions
  - Broadcast events via EventHub
  - Log execution results

*** Storage Layer
- *Database*: SQLite at =~/.vibecare/vibecare.db=
- *Migration Tool*: Goose (not go-migrate)
- *Schema*:
  - =profiles= - User profiles
  - =devices= - Registered devices
  - =routines= - Routine metadata (no embedded actions)
  - =schedules= - Schedule definitions with RRule strings
  - =actions= - Individual actions
  - =schedule_actions= - Join table (schedule_id, action_id, action_order)
  - =execution_logs= - Audit trail
  - =icons= - SVG icon metadata
  - =schedule_templates= - Template definitions

*** HTTP Web Server
- *Port*: 8080 (default)
- *Endpoints*:
  - =GET /status= - Server health check
  - =GET /api/icons/{id}.svg= - Serve SVG icons
  - =GET /api/templates= - List schedule templates
  - =GET /api/templates/{id}= - Get template details

*** EventHub
- *Pattern*: Server-Sent Events (SSE)
- *Events*:
  - =scheduleTriggered= - Schedule became due
  - =routineExecuted= - Routine finished execution
- *Per-Profile Channels*: Each profile has dedicated event stream

** Database Schema Details

*** Schedule-Action Relationship

*Architecture Decision*: Actions are *not embedded* in schedules. Instead, they're associated via a join table.

#+BEGIN_SRC sql
CREATE TABLE schedule_actions (
    schedule_id TEXT NOT NULL,
    action_id TEXT NOT NULL,
    action_order INTEGER NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (schedule_id, action_id),
    FOREIGN KEY (schedule_id) REFERENCES schedules(id) ON DELETE CASCADE,
    FOREIGN KEY (action_id) REFERENCES actions(id) ON DELETE CASCADE
);
#+END_SRC

*Benefits*:
- Actions can be reused across schedules
- Ordering maintained via =action_order= field
- Bulk updates via =replaceScheduleActions= RPC
- Cascading deletes handled by DB

*** RRule Storage

Schedules store RRule strings directly:

#+BEGIN_SRC sql
CREATE TABLE schedules (
    id TEXT PRIMARY KEY,
    profile_id TEXT NOT NULL,
    routine_id TEXT NOT NULL,
    name TEXT NOT NULL,
    rrule TEXT NOT NULL,  -- RFC 5545 RRule string
    dtstart DATETIME NOT NULL,
    priority TEXT DEFAULT 'none',
    enabled BOOLEAN DEFAULT TRUE,
    -- ... other fields
);
#+END_SRC

*Example RRule*:
#+BEGIN_EXAMPLE
FREQ=DAILY;INTERVAL=1;BYHOUR=9;BYMINUTE=0
#+END_EXAMPLE

Means: "Daily at 9:00 AM"

** MVVM Layers

*** Models
Simple Swift structs conforming to:
- =Identifiable= - For SwiftUI lists
- =Codable= - For JSON serialization
- =Equatable= - For value comparison
- =Hashable= - For Set/Dictionary usage
- =Sendable= - For Swift concurrency

*No persistence annotations* (no @Model, @Entity, etc.)

*** Views
SwiftUI views organized by feature:
- *Actions/*: Action management UI
- *Routines/*: Routine CRUD and list views
- *Schedules/*: Schedule creation, editing, RRule builder
- *Settings/*: Network config, preferences
- *Dashboard/*: Main overview

All views are *stateless* - state lives in ViewModels.

*** ViewModels
Manage feature state with =@Published= properties:

#+BEGIN_SRC swift

        do {

    }

- Created when view appears
- Destroyed when view disappears
- *No persistence* - data refetched on next view appearance

** Service Layer Details

*** GRPCClientManager: Connection Lifecycle

*Pattern*: =withXServiceClient= provides automatic connection management:

#+BEGIN_SRC swift
func withRoutineServiceClient<T>(
    _ body: (VCRoutineServiceAsyncClient) async throws -> T
) async throws -> T {
    let channel = try makeGRPCChannel()  // Create connection
    let client = VCRoutineServiceAsyncClient(channel: channel)
    defer { try? channel.close().wait() }  // Always close
    return try await body(client)
}
#+END_SRC

*Benefits*:
- No connection leaks
- Automatic error handling
- Centralized configuration
- gRPC interceptor support

*** EventService: Real-Time Updates

*Purpose*: Listen for backend events and execute actions locally.

*Flow*:

#+BEGIN_SRC swift
func startListening(for profileId: String) async {
    try await GRPCClientManager.shared.withEventServiceClient { client in
        let request = VCStreamEventsRequest(profileId: profileId)
        for try await event in client.streamEvents(request) {
            switch event.eventType {
            case .scheduleTriggered:
                await handleScheduleTriggered(event)
            case .routineExecuted:
                await handleRoutineExecuted(event)
            }
        }
    }
}

private func handleScheduleTriggered(_ event: VCEvent) async {
    // 1. Fetch schedule details
    let schedule = try await scheduleService.getSchedule(event.scheduleId)

    // 2. Fetch actions from schedule_actions table
    let actions = try await scheduleService.getScheduleActions(event.scheduleId)

    // 3. Execute each action
    for action in actions {
        switch action.type {
        case .notification:
            NotificationManager.shared.show(...)
        case .open_link:
            NSWorkspace.shared.open(URL(string: action.parameters["url"]))
        case .run_script:
            // Execute shell command
        }
    }

    // 4. Broadcast to UI
    NotificationCenter.default.post(name: .routineDidExecute, ...)
}
#+END_SRC

* Architecture Decisions

** ADR-001: Server-First Frontend (No Local Persistence)

*** Context
Early versions had local SQLite + sync managers for offline-first functionality.

*** Decision
Removed all local persistence. Frontend is now server-centric:
- No local database
- No sync managers
- No conflict resolution
- All state transient (in-memory ViewModels)

*** Consequences

*Benefits*:
- Simpler codebase (no sync complexity)
- Backend is single source of truth
- No data inconsistencies
- Easier debugging (one DB to inspect)

*Drawbacks*:
- No offline functionality
- Requires active backend connection
- State lost on app restart
- Network errors more disruptive

*** Rationale
For a personal wellness app, offline support is less critical than simplicity.
Users typically run both backend and frontend on same machine.

** ADR-002: Schedule-Action Join Table

*** Context
Need to associate actions with schedules.

*** Decision
Use join table =schedule_actions= instead of embedding action IDs in schedule.

*** Consequences

*Benefits*:
- Actions reusable across schedules
- Ordering via =action_order= field
- Bulk updates efficient
- Cascading deletes handled by DB

*Drawbacks*:
- Extra DB queries to fetch actions
- More complex data model

*** Rationale
Flexibility and reusability outweigh query complexity.

** ADR-003: Backend-Served Icons

*** Context
Icons needed for routines, actions, notifications.

*** Decision
Serve icons from backend HTTP API instead of bundling in app.

*** Consequences

*Benefits*:
- Dynamic icon updates without app release
- Centralized icon management
- Smaller app bundle
- Icons shared across platforms (future web/mobile)

*Drawbacks*:
- Network request required for each icon
- Requires backend running
- No offline icon display

*** Rationale
Supports future multi-platform expansion and easier icon management.

** ADR-004: VibeNotify for Notifications

*** Context
macOS native notifications have limited customization.

*** Decision
Use custom VibeNotify library instead of =UNUserNotificationCenter=.

*** Consequences

*Benefits*:
- Full control over styling
- Custom positioning
- Interactive actions without notification center permissions
- Better UX for wellness reminders

*Drawbacks*:
- Additional dependency
- Notifications don't persist in notification center
- No system-level notification history

*** Rationale
Better UX for immediate, actionable wellness reminders outweighs lack of persistence.
